# Test Design Standard — Requirements-Traced Automated Tests

Version 1.0 · Draft for adoption · Applies to all automated test suites, whether authored by
engineers or generated by AI coding agents.

## 1. Purpose

This standard defines the conditions under which an automated test is accepted into a project test
suite. It exists to ensure that every accepted test verifies a requirement and is capable of
detecting a fault. It applies equally to tests written by hand and to tests generated by an AI
coding agent.

## 2. Scope

Applies to unit, integration, API, authorization, and validation tests. Does not prescribe test
frameworks, file layout, or naming conventions beyond the traceability requirements in clause 6.

## 4. Terms and definitions

4.1 **Requirement.** A statement of behavior the system shall exhibit, owned by the product owner or
responsible engineer.

4.2 **Provenance.** The documented origin of a requirement. Permitted values: *specification*,
*owner decision*, *existing implementation*, *assumption*.

4.3 **Assumption.** A requirement drafted by an agent or engineer for which no specification and no
owner decision exists.

4.4 **Characterization test.** A test whose expected value is derived from the current behavior of
the implementation rather than from a requirement. Characterization tests encode defects present in
the implementation at the time of writing.

4.5 **Traced test.** A test linked to exactly one requirement identifier whose assertion verifies
that requirement.

4.6 **Redundant test.** A test that kills no mutant that is not also killed by another test in the
suite.

4.7 **Mutation score.** The proportion of generated mutants killed by the test suite, as reported by
a mutation testing tool.

## 5. Requirements ownership

5.1 Requirements shall be decided by the product owner or responsible engineer. An AI coding agent
may draft requirements but shall not decide them.

5.2 Every requirement shall carry a provenance value as defined in 4.2.

5.3 A requirement whose provenance is *assumption* shall be submitted to the owner for decision
before any test is written against it. The agent shall not substitute a default value for an
undecided requirement.

5.4 A requirement whose provenance is *existing implementation* shall be reviewed by the owner for
correctness before it is accepted, because the implementation may contain defects.

## 6. Traceability

6.1 Each accepted test shall trace to exactly one requirement identifier. The identifier and the
requirement's provenance shall appear in a comment adjacent to the test.

6.2 Each requirement shall be verified by at least one test.

6.3 A test that traces to no requirement shall not be accepted. Such a test is redundant by
construction and shall be removed or given a requirement.

6.4 Two tests that trace to the same requirement and differ only in input data shall be
consolidated into one test, unless a boundary defined in the requirement justifies the second
input.

## 7. Test construction

7.1 Assertions shall verify observable outcomes: response status, response body, persisted state,
or emitted events.

7.2 Assertions shall not verify implementation internals, including call counts on collaborators,
private state, or the exact wording of error messages unless the wording is itself a requirement.

7.3 Tests shall not verify framework or library behavior.

7.4 Where the implementation exists at the time of writing, the author shall demonstrate that the
test fails when the requirement is violated (for example, by temporarily disabling the
corresponding check) before the test is accepted.

7.5 A test shall not be modified to pass by skipping it, isolating it with a focus marker, or
removing an assertion. A failing test shall be reported to the owner.

## 8. Verification of the suite

8.1 Fault detection capability shall be measured by mutation testing. Line or branch coverage
shall not be used as evidence of fault detection capability.

8.2 The mutation testing tool's own report shall be the record of results. Summaries produced by an
AI agent shall not substitute for the report.

8.3 A surviving mutant on a line exercised by the suite indicates that the exercising tests are
pseudo-tested or tautological with respect to that line, and shall be investigated.

8.4 A surviving mutant on a line not exercised by any test indicates a missing requirement or a
missing test, and shall be recorded as a gap.

8.5 A mutant judged equivalent (no observable effect) shall be recorded with a one-line
justification and excluded from the score.

8.6 Per-test kill data shall be retained so that redundant tests (4.6) can be identified.

## 9. Review procedure for existing suites

9.1 The reviewer shall first derive the requirement list from the suite, grouping tests by the
requirement each claims to verify.

9.2 The reviewer shall then apply clause 8 to the suite.

9.3 Only tests unresolved by 9.1 and 9.2 shall be examined individually.

9.4 The review output shall list: the requirement table with provenance; tests classified as
characterization, pseudo-tested, tautological, redundant, over-specified, or non-failing; gaps; and
proposed actions. No action shall be taken without owner approval.

## 10. Limits of this standard

10.1 Compliance establishes that each test verifies a stated requirement and can detect a fault. It
does not establish that the requirements themselves are correct. Requirement correctness remains
the responsibility of the owner under clause 5.

10.2 Mutation testing measures detection of changes to the current implementation. It does not
detect that the current implementation is wrong.
